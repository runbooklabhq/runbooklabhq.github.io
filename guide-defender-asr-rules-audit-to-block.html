Defender ASR rules: from Audit to Block without breaking things

Attack surface reduction rules stop Office macros, scripts and credential theft before they run. Turned on in Block mode all at once, they also stop the finance team's macro and the backup agent. Six steps to roll them out in rings, starting with read-only checks.

The six steps

1. Read what is set today

Read-only, on a sample device. Actions: 0 off, 1 Block, 2 Audit, 6 Warn.

$p = Get-MpPreference
$i = 0
foreach ($id in $p.AttackSurfaceReductionRules_Ids) {
  [pscustomobject]@{ Rule = $id
    Action = $p.AttackSurfaceReductionRules_Actions[$i] }
  $i++ }

2. Put every rule in Audit

Intune > Endpoint security > Attack surface reduction > create an ASR rules policy, all rules on Audit, assigned to all devices. Leave it for two to four weeks so month-end jobs show up too.

3. Find the noisy rules

Defender portal > Advanced hunting (Plan 2 / E5). On Business Premium use Reports > Attack surface reduction rules instead.

DeviceEvents
| where Timestamp > ago(30d)
| where ActionType startswith "Asr"
| summarize Events = count(), Devices = dcount(DeviceId)
    by ActionType, FileName, InitiatingProcessFileName
| order by Events desc

4. Add narrow exclusions

One exclusion per legitimate tool, as a full file path, per rule where you can. No folder-wide or wildcard exclusions, and never exclude a whole user profile. Give every exclusion an owner and a review date in your tracker.

5. Move to Warn, then Block, in rings

Ring 0: IT devices. Ring 1: a pilot group of 5–10% of users. Ring 2: everyone. Warn lets a user unblock once, so it shows you what still breaks; a few rules don't support Warn, so check Microsoft's rule reference.

6. Keep watching

Re-run the step 3 query weekly. A rule that suddenly fires hundreds of times a day is either a new tool that needs an exclusion or an attack. Both need an owner.

FAQ

Should I turn on attack surface reduction rules in Block mode straight away?

No. Start every rule in Audit mode for two to four weeks, review what would have been blocked, add narrow exclusions for legitimate tools, then move rules to Warn or Block in rings: IT devices first, then a pilot group, then everyone.

How do I see which ASR rules are active on a Windows device?

Run Get-MpPreference in PowerShell and read AttackSurfaceReductionRules_Ids and AttackSurfaceReductionRules_Actions. The action values are 0 = off, 1 = Block, 2 = Audit, 6 = Warn. This only reads settings and changes nothing.

How do I find ASR audit events in Microsoft Defender?

In Advanced hunting, query DeviceEvents where ActionType starts with Asr. Events ending in Audited are what the rule would have blocked; events ending in Blocked were stopped. Group by rule, file and initiating process to find the noisy ones.

Which ASR rules are safest to block first?

Microsoft lists three standard protection rules with minimal compatibility impact: Block credential stealing from the Windows local security authority subsystem (LSASS), Block abuse of exploited vulnerable signed drivers, and Block persistence through WMI event subscription. Still audit them first in your own environment.
